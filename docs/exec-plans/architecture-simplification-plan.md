# 架构减法计划：吸收 LinkSense 的简单做法

状态：**提议，未批准**。本文不修改任何现行契约；每个切片落地时再更新对应的 owning 文档和 ADR。

核对基线：ai-platform `55ef9eda`（main，2026-11-12），LinkSense `d63c77ef`（main，2026-11-13）。
LinkSense 采用 CPAL-1.0，本计划只借鉴设计，不复制源码。

关联：#1961（两项目架构对比）、#1953（生命周期实测）、#1956（Attempt 唯一结算）。

## 1. 结论

LinkSense 整体并不比我们小（API 15.5 万行、Runner 4 万行，`process-pool.ts` 单文件 8360 行）。
它简单的地方只在**执行主链的状态模型**，而这正是我们最重的地方。差异来自四个设计选择：

| | LinkSense | ai-platform 现状 | 我们为此付出的代价 |
|---|---|---|---|
| 环境寿命 | Worker 和原生进程按会话存活，空闲 900 秒后回收 | 沙箱寿命等于一次 Run/Attempt | 每轮创建、探测、复制恢复工作区；每轮结束 stop + save；停止必须做快照和续聊结算 |
| 会话记录 | 原生线程留在工作区磁盘，下一轮直接续 | SDK 会话逐条镜像进 PG（6 张 `provider_session_*` 表、epoch、回执、writer 校验） | `writer_unverified` 锁死续聊、`recovery_candidate`、隔离对账 |
| 事件回放 | PG 一张 `conversation_events` 是回放权威；Redis Pub/Sub 只唤醒；心跳也触发补读 | 事件同时写 PG 和 Redis Stream，但只允许从 Redis 回放 | `stream.gap` 后只能轮询到终态；Redis 发布失败让已落库的回调返回 503；incarnation/authority lease 等 5 张表 |
| 终态归属 | 原生 `turn/completed` 是事实，数据库只投影；不重试整轮、不重发输入 | Run、Attempt、sandbox lease、queue lease 各有状态机，互相结算 | `runs` 约 90 列、`sandbox_leases` 约 60 列；对账器、转发器、结算 shadow |

所以减法的核心只有一句：**让运行环境活得比一轮长，让 PG 里已有的事实直接可用**。
做到这两点，续聊、停止、刷新恢复这三类问题的大部分机制会变成只在崩溃路径上才需要。

## 2. 吸收的原则

每条都在 LinkSense 源码或其设计文档中核对过。

1. **环境寿命长于一轮，授权每轮重验。** 复用的是计算和文件，不是权限。
2. **原生终态是事实。** 平台不用数据库状态替代 SDK 的结果，不为传输故障重跑 Agent。（我们已在 #1956 的"以执行结果为准"中采用。）
3. **持久事件表是回放权威，消息通道只负责快。** 通道丢消息只影响延迟，不影响正确性。
4. **停止直达执行器。** 持久意图只为"还没启动"和"进程丢失"兜底。
5. **Provider 是运行时事实来源，数据库是缓存和审计。** 对账只处理孤儿和分歧，不参与正常路径。
6. **可选依赖不阻塞启动。** 一个慢 MCP 不应拖住整个 Agent。

## 3. 不吸收的

- 用户级共享 Worker：同一用户所有会话共用环境，隔离弱于我们按会话的目标。
- Controller 挂 Docker socket：我们的默认部署不挂，保持。
- 8360 行的进程池单文件、Codex 专用事件映射：与我们的 Claude SDK 无关。
- 知识库、应用市场、渠道、计费等产品面：不在本计划内。
- 本地磁盘 outbox：我们的回调已先落 PG，再加一层 outbox 是重复。

## 4. 切片

按"收益 ÷ 风险"排序。每个切片必须净减代码，并写明删除了什么。

### S0 收口在途工作（前置）

- 合并 #1956：Attempt 成为唯一结算权威，退役 legacy 8 字段和 shadow 双写。合并前在当前 head 重跑 s72 验收。
- 在途 20 个 Draft PR 按 #1961 的处置清单办：先合 4 个小 PR 和 #1957，9 个过时或纯搬家的关闭，#1958 暂缓。

### S1 事件：PG 回放，Redis 只加速（已确认，ADR 0018）

改动：
- `stream.gap` 或无游标重连时，API 从 `run_events` 按序号回放，再接上 Redis 实时流。不再"只轮询到终态"。
- 回调在 PG 提交后即返回成功；Redis 发布失败只记指标，由回放补齐。

删除：`503 callback_stream_unavailable` 分支、前端 gap 轮询分支；随后退役 `sse_stream_authorities`、`sse_authority_leases`、`run_event_terminal_drains`、`run_event_cursors`、`run_event_batches` 中不再被读取的部分。

需要的决定：**修订 ADR 0013**（它禁止从 PG 回放）。
解决：#1961 的 S2、S3、F4。
验收：流被裁剪后刷新，正文连续不重复；停 Redis 期间工具继续执行，恢复后页面补齐。

### S2 会话级运行环境（已确认，ADR 0017）

改动：
- Run 结束后沙箱和执行器不销毁，进入空闲状态，默认保留 15 分钟；同一会话的下一轮直接复用，SDK 用原生 `resume` 续接留在沙箱内的会话。
- 工作区保存从"每轮结束必做"改成"空闲回收时做一次"；成果文件仍在本轮结束时登记到对象存储。
- 每轮仍重新校验主体、专家、模型、工具授权，并签发新的模型凭据。
- 失效条件：专家或 Skill 版本变化、镜像变化、外部效果不明、空闲超时、沙箱不健康。任一成立则走现有的冷启动加恢复路径。

删除（正常路径上）：每轮 `create` + 双重就绪探测、每轮工作区复制恢复、完成前的 stop provider + save 屏障、停止快照与续聊结算。这些保留为冷路径，不再影响每轮时延。
随后可收缩：`provider_session_*` 镜像降为回收时的备份；`sandbox_leases` 退回纯资源记录。

需要的决定：**隔离范围从"每轮"变为"每会话"**，更新 `sandbox-runtime-control-layer.md` 和 `claude-provider-session-continuity.md`。
解决：#1961 的 F1、F2、F5，以及 #1899 一类"停止后不能续聊"的问题根源。
先做试验：同模型同输入，对比第二轮的首字时延、复制字节数、停止到可再发送的时间，再决定是否全量替换。计时口径先按 #1953 修正。

### S3 停止直达

改动：取消意图落库后，API 立即尽力调用一次执行器取消；现有 1 秒转发器降为兜底。
删除：无新增状态；S2 落地后，转发器只服务于进程丢失。
解决：F6。

### S4 MCP 单连接、不阻塞

改动：每个 server 一条连接，发现和调用共用，按操作设预算；慢 server 超时后本轮标记不可用，SDK 先启动。
保留：逐工具授权、凭据刷新、写操作结果不明保护。
解决：F3。

### S5 准入（S1、S2 之后再评估）

候选：用 PG 的 `for update skip locked` 取代 Redis 队列。Run 入库即入队，消除"PG 已提交但 Redis 未入队"这一类状态（`accepted_pending_enqueue`、`retry-admission`、队列 lease 回收）。
`app/queue.py` 现为 2611 行。这是较大的替换，先不承诺。

### S6 过程减负

- 测试代码 25.7 万行，是应用代码的 1.8 倍；文档 84 份，其中 SSE 有 6 份 ADR。新增机制前先问"它保护哪一个独立事实"。
- 切片的完成条件增加一条：净行数为负，或说明为什么不是。
- 表数量目标：68 张降到 55 张以内（S1 约 4 张，S2 约 4 张，#1956 已含部分）。

# ADR 0016: Run 的持久执行、结果结算与资源回收

## Status

Proposed（待评审）。本 ADR 不改变现行行为；现行合同仍以 [ADR 0011](0011-durable-executor-terminalization.md)、
[Runtime authorities](../architecture/runtime-authorities.md)、
[ExecutionSpec and RunAttempt](../architecture/execution-spec-and-attempt-lifecycle.md) 和
[Sandbox Runtime](../architecture/sandbox-runtime-control-layer.md) 为准。事实盘点见
[执行链路状态盘点](../exec-plans/execution-chain-state-inventory.md)。

## Context

近 60 天修复集中在执行链路，盘点发现：一个沙箱任务跨 6 个状态维度，终态可从 10 条路径到达，
多处重复定义状态集合与拼写，租约表有两个写入方，终态组合服务有两套同构包装。

简化目标不是先固定“几个状态机、几条路径”，而是用一次 Run 的完整时序和故障窗口推导必要状态，
删除只因路径分散而产生的状态与判断。

### 一次 Run 的完整阶段

| 阶段 | 必须完成的事 | 进入下一阶段的依据 |
|---|---|---|
| 1 请求准入 | 用户、Session、Profile、模型、Skill/MCP、附件授权；提交幂等 | 确定性拒绝不创建 Run；提交结果不确定时不得宣称未创建 |
| 2 持久接受 | 用户消息、Context 绑定、Run 与提交记录 | PostgreSQL 提交；可以有 Run 而无 Attempt |
| 3 排队投递 | 投递队列，处理入队响应丢失 | 精确身份的入队确认，或可恢复的待投递记录（现为 `accepted_pending_enqueue`） |
| 4 执行准入 | 重新授权、准备上下文、冻结 ExecutionSpec、创建并领取 Attempt | Spec、Attempt、owner 的持久绑定 |
| 5 准备沙箱 | 创建资源、验证身份、准备工作区、输入文件、Skills 与受限凭据 | 资源与 Attempt 绑定可验证；中途失败有补偿 |
| 6 交付执行 | 启动沙箱内 Agent，记录接受执行事实 | 区分“明确拒绝”与“已接受但响应丢失”；允许终态回调早于接受记录 |
| 7 执行与交互 | 模型/工具循环、进度、答案流、会话持久化、取消 | 心跳只证明活动；浏览器断线不改变执行结果 |
| 8 接收结束证据 | 确认 SDK 完成、流与 SessionStore 收尾、保存终态回执 | 原 Attempt 的合法、幂等、不可随意覆盖的结果证据 |
| 9 结算交付 | 校验答案回执、收集选定文件、生成不可变快照写对象存储 | 满足平台交付合同；临时对象有回收责任 |
| 10 提交业务结果 | 原子提交 assistant、产物、原生会话覆盖、Run/Attempt 终态与事件 | **数据库事务提交：平台结果成立点** |
| 11 展示与回读 | 发布 SSE、浏览器同步、历史与附件可读 | 通知失败可重新读取，不能重新执行 |
| 12 清理与下一轮 | 停止并释放资源、补偿孤儿对象；下一轮重新授权并恢复原生会话 | 清理有独立完成证据；续接不得静默降级为空会话 |

## Decision

### D1 安全边界保持不变

整个 Agent（SDK、内置工具、工具子进程、sidecar）运行在绑定精确 Run/Attempt 的受管沙箱内。
沙箱内不放平台数据库凭据；模型访问经代理并使用 Attempt 绑定的受限凭据。本 ADR 不新增网络隔离承诺；
现行内部测试网络合同“不作生产隔离承诺”的表述保持不变。引擎品牌（Claude、pi 等）不改变这一边界。

### D2 三个主体，按职责收窄

| 主体 | 职责 | 不负责 |
|---|---|---|
| Run | 持久接受的业务请求、取消意图、最终交付结果；**唯一的业务结算权**，包括尚无 Attempt 时的失败 | 单次执行身份与执行凭据 |
| Attempt | 冻结的执行输入、执行权、交付事实、执行证据与结算进度 | 业务授权的全部判断 |
| SandboxResource | 精确资源身份、可用性、停止与释放证据、失败补偿；可在业务结束后继续清理 | 判断 Run 是否成功 |

Runs 应用服务是 Run 终态的唯一写入方；存在 Attempt 时，在同一事务内校验并结算该精确 Attempt。

### D3 四种“完成”分开记录，顺序固定

`SDK 完成（终态回执持久化）→ 业务结算（阶段 10 事务）→ 用户取得结果（发布/回读）→ 资源释放`。
每一项有独立的持久证据与恢复规则，不由一个终态字段同时表示。发布失败不回滚已提交结果
（保持现有 `worker_publication_v4` 行为）。

### D4 区分四类并发控制，不共享一个数字

- **执行权代际**：现有 `owner_generation`，只在执行所有权变化时使用；结算、重试与阶段推进
  不得撤销当前执行凭据，也不得让旧执行者凭新代际重新获得权限。
- **状态迁移 CAS**：行级版本或期望状态校验。
- **结算操作认领**：认领、退避、重试。
- **资源操作认领**：停止、释放、隔离的认领。

四者统一由 PostgreSQL 管理。不新增会触发 `owner_generation` 递增的普通阶段迁移；
如需表示“已收到终态、正在结算”，作为 Attempt 的结算字段而非新的执行状态，
并同步调整 `commit_provider_turn` 的前置条件（当前要求 Attempt 为 `running`），具体在 Phase 3 设计评审中确定。

### D5 两种停止顺序

- 正常完成：`保存终态证据 → 收集产物 → 提交业务结果 → 停止并释放资源`。
- 取消/超时：`持久取消意图 → 撤销执行权限并通知停止 → 宽限期后强停 → 结算结果 → 继续清理`。

判定失败或取消不证明远端已停止；停止结果未知时，业务可以结束等待，资源记录保留清理责任。

### D6 失败分类

- 执行丢失（心跳/派发超时且无终态回执）→ 由监督者判定失败；**失联不等于无外部副作用**，
  `mcp_execution_outcome_unknown` 等不确定结果继续阻止自动重试。
- 已有终态回执后的结算失败：永久的校验/权威错误 → `failed`（`terminal_reconciliation_failed`）；
  临时依赖错误 → 保留回执、退避重试（沿用 ADR 0011）。
- 单次结算操作超时与“产品允许放弃结算的总期限”是两个概念；后者是新的产品决策（见待决事项 Q1）。

### D7 统一入口，不统一凭据

执行器上报（心跳、进度、答案片段、原生会话追加、终态回执）共用一个身份验证与接收框架，
内部保留明确类型和各自的校验、幂等规则。必须区分：私有执行证据与公开 `run_events`；
数据库已接收与通知已送达；重复事件与内容冲突的终态；执行器回报与探测推断。

### D8 跨存储交接走持久意图

PostgreSQL 决定“需要投递/恢复”的事实以持久记录（outbox 或可重建扫描）表示；Redis 至少一次投递，
消费者凭持久身份幂等领取。首次投递不依赖尚未创建的 Attempt。Redis 不参与所有权与终态判断；
其对账 fence 在 outbox 与统一监督者验证后退役。

### D9 监督与后台职责

一个调度框架按显式截止时间触发：排队等待、派发、心跳、取消宽限、单次结算操作。
投递补偿、资源清理与孤儿回收由同一框架触发，但各自保留完成证据。
任何时刻每类裁决只有一个权威执行方；迁移期间新旧监督者不得同时裁决。

### D10 迁移规则

每一步写明：最低兼容版本、在途任务排空条件、历史记录读法、退役清单。
新字段先作影子数据验证；删除旧列是单向操作，删除前确认旧二进制不再运行。

## Implementation plan

| Phase | 内容 | 退出条件 | 风险 |
|---|---|---|---|
| 0 映射与回归 | (a) 为上表 12 个阶段写出事实 owner、持久凭据、外部副作用、崩溃恢复方式；(b) 建真实链路回归（见下） | 现有 main 上回归全部通过，或失败项登记为缺陷 | 无行为变更 |
| 1 去重，语义不变 | 唯一状态词表与历史归一化读取；数据审计后为 `runs.status` 加约束（`dead_letter` 含义保留）；合并 `*_with_context`/`*_with_v4`；`sandbox_leases` 单一写入方并归入 Sandbox 上下文 | 回归通过；重复定义清单检索为空 | 低 |
| 2 显式阶段与交接 | 本 ADR 评审通过；类型化统一入口（来源、冲突检测）；交付接受事实（拒绝 vs 响应丢失，允许回调早到）；投递 outbox | 回归通过；新增场景通过 | 中 |
| 3 结算字段与统一监督 | Attempt 结算字段以影子方式写入并比对；调整会话提交前置条件；统一监督者按截止时间逐条替换过期回收、探测调度、异常兜底（逐条开关，旧路径同步停用） | 影子比对在约定观察期内零偏差；回归通过 | 高，需设计评审 |
| 4 切换与退役 | 读取切换到 Attempt；停写租约执行/对账列；排空在途任务后删列；SandboxResource 只管资源；退役 Redis 对账 fence | 退役清单与检索为空；文档更新 | 高，单向 |

引擎适配（pi、ACP）延后，不在本 ADR 范围；其接入须复用上述阶段与凭据，不新增终态回调协议。

### 回归场景（Phase 0 建立，后续每个生命周期 PR 必跑）

正常完成、用户取消、执行超时、沙箱容器崩溃、回调丢失（仅探测发现）、重复回调、交付后 Worker 崩溃、
产物回收失败；以及入队 ACK 丢失、执行接受 ACK 丢失、回调早于接受记录、对象写入后事务回滚、
终态提交后通知失败、下一轮原生会话续接。

除最终状态外必须断言不变量：旧 owner 不能写入；新 Attempt 不重复执行未确认的副作用；
结算重试不重复生成答案或产物；清理失败不改写已提交结果；续接不降级为空会话。

## Open questions

- Q1 是否设置“放弃结算”的总期限？ADR 0011 现为临时错误不设上限；如设置，到期后的用户结果与回执处理需定义。
- Q2 `finalizing` 是否作为公开阶段展示？
- Q3 `waiting_input` 暂不进入公开 Run 状态，待定义输入请求持久化、回答关联、超时与重启恢复后再议。
- Q4 真实链路回归在哪个环境运行（CI 的 Docker、s72 隔离环境），以及是否作为生命周期 PR 的必需检查。

## Alternatives considered

- **“循环在受信进程、只有工具进沙箱”**：Claude Agent SDK 的内置工具、stdio MCP、Skill 脚本与 hooks
  在 SDK 所在环境执行，多租户下循环进程本身是攻击面；不采用（D1）。
- **引入 Temporal 等工作流引擎**：其区分排队、单次执行、整体执行与心跳超时，可承担调度；
  但不替代产物提交、会话续接与外部副作用的幂等边界，且新增重量级依赖。保留为对比选项，Phase 3 前复评。
- **以单一终态字段与单一代际统一裁决**：会使结算推进撤销执行凭据，并与原生会话提交条件冲突（D4）；不采用。

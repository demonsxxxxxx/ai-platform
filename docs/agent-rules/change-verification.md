# 变更验证：先选对场景，再补失效证据

状态：当前仓库工作规范。本文拥有修改前验收场景、修改反馈、检查选择和证据复用规则；不新增审批、固定全套检查或任务台账。

[本地测试执行](local-test-execution.md)继续拥有 pytest runner、隔离、超时及证据文件；[证据治理](../architecture/ci-test-readiness-governance.md)拥有证据等级和强制 CI；[交付流程](github-issue-pr-workflow.md)拥有 PR、审查及发布边界。本文不降低这些要求。

## 1. 修改前把用户要求变成可观察的结果

- 在当前任务或 PR 中简短列出删除、保留、对齐、默认状态及交互要求。小改动可直接说明结果，不另建清单文件、阶段台账或审批步骤。
- 不得把“删除内容”自行解释为“调整排版”，也不得用更简单的实现静默省略要求。截图标记的歧义确实影响结果时先澄清；已明确的要求直接执行。
- 先读受影响代码、直接调用方、现有测试和 owning contract，确认修改要到达的消费者及可能破坏的行为。没有影响的区域不纳入重构或验证范围。

## 2. 先复现最可能暴露问题的场景

选择会改变行为或布局的输入和状态，而不是最容易通过的演示数据。缺陷修复先建立能捕捉用户症状的最小可运行反馈；已有回归能捕捉时直接复用。页面打开、无报错、单条数据截图不能证明满载布局正确。

例如，表格与分页的布局修改应覆盖空结果、单条、满页和多页末页；有展开内容时检查展开态。数据按实际页大小构造，不固定要求某个用户数量。响应式布局先查最容易出问题的满页、展开和较矮视口，再检查其他受影响主题或宽度，不把所有维度机械相乘。前端具体渲染要求见[前端指令](../../frontend/web/AGENTS.md)。

这些是按风险选场景的示例，不是所有任务的统一测试矩阵。纯文档修改检查文档和链接，不运行无关运行时验证。

## 3. 每种检查只证明它实际覆盖的部分

| 检查 | 主要证明 | 不能替代 |
| --- | --- | --- |
| 行为回归 | 查询、分页、排序、取消、状态、数据归属及失败路径 | 像素尺寸、裁切、滚动与真实焦点行为 |
| 浏览器实际页面 | 对齐、可达性、滚动、响应式、主题及相关交互 | 未调用的真实服务、后端或全量业务正确性 |
| 类型、Lint、构建 | 对应静态约束及产物能否生成 | 功能和视觉验收 |
| 源码库存或合同检查 | 入口、依赖、消费者、选择器和退役路径 | 实际交互与渲染 |

JSDOM 可以验证挂载、状态和事件，不提供真实布局证据。设计图或样式样稿获批也不等于实际页面验收。报告采用[证据等级](../architecture/ci-test-readiness-governance.md#2-evidence-levels)，不以检查数量代替覆盖说明。

## 4. 同一问题成组修改，用最快的有效反馈收敛

理解根因后，完成该问题及其直接消费者、回归、选择器和文档所需的最小完整修改，再检验同一场景。不要逐文件完成后就启动整套检查，也不要把无关清理混入变更。

迭代时选择能捕捉当前问题的最快检查。纯样式调整优先使用实际页面预览检查受影响几何；不因每次间距、颜色或局部文案变化都重新完整构建。行为变更先运行 owning 回归。失败后按证据修复，再复验受影响部分，不盲目重跑未改变的失败动作。

## 5. 按修改影响判断哪些证据失效

只有代码、输入、依赖或运行条件的变化可能影响某项结论时，才需要补验该结论；存在反例或实际失败时，相应证据立即失效。相同条件下仍有效的结果继续使用，不为“放心”重复检查。

- **只改样式：**重验受影响布局和相关交互；未改变的业务测试结果可复用。
- **改请求、状态或分页逻辑：**运行 owning 回归与直接受影响的交互，保留数据、取消、隔离和失败路径检查。
- **改文案或删除说明：**读完整受影响文案及其界面上下文，核对消费者、必要缺席检查与 owning 文档；仅在尺寸或交互可能变化时补渲染检查。
- **改共享组件、依赖或检查入口：**追踪实际受影响调用方及其必要合同检查；范围由依赖和风险决定，不默认扩展到全仓库。

证据只能用于它覆盖的候选和输入。不得将旧提交的 CI、旧构建截图或相邻工作区结果直接标为新候选通过；保留未受影响的局部结论时说明其适用范围，不改写原结果的来源。

## 6. 收敛后集中检查最终候选

修改收敛后，对实际候选集中执行相关静态检查、必要构建、owning 回归和实际页面验收；独立且不争用测试环境的检查可以并行。复用已有脚本及检查入口，短小任务不另建验证平台。

生产预览依赖构建产物时，必须更新产物后再验收；不能拿旧 dist 的页面证明新源码。最终候选又有修改时，只补因此失效的检查。项目强制检查、真实依赖/零跳过要求和 CI 门禁始终有效，不得通过弱化断言、隐藏失败、增加跳过或降低规则让候选通过。

交付时说明结果、关键数据规模或场景、实际通过与失败的检查及必要限制。区分逻辑、视觉、构建、CI 和真实服务结果，不用“已全面检查”概括有限证据。无需在回复中展开原始日志或维护另一份验证台账。
